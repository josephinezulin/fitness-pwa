# 第三階段：Apple 健康與 iOS 捷徑（規格，尚未安裝）

依賴第二階段的安全 API 已驗證。PWA 無法直接讀取 Apple Health；只能由使用者授權的 iOS 捷徑讀取。每日自動化並非可靠背景排程，鎖定時某些健康資料受保護，動作可能必須解鎖／確認；iOS 升級後需重測。

## 使用者手動步驟

1. 捷徑 App 建立「同步日常動作」，分別授予體重、體脂率、選定心率類型、步數的唯讀權限。拒絕權限不得視為數值 0。
2. 設定裝置 ID、日摘要時區，以及只存在捷徑與 Script Properties 的高熵可撤銷裝置憑證。捷徑不提供硬體安全保管；可開啟／分享捷徑的人可能取得憑證，不分享含憑證版本。若無法接受此風險，改用每次互動 OAuth 授權並放棄無人值守同步。
3. 首次手動執行，解鎖 iPhone，確認健康與網路權限。以虛構／最小樣本完成 API 驗收後才寫入正式表。
4. 個人自動化 → 特定時間 → 每日，例如 21:30 → 執行同步捷徑。若系統提供「立即執行」可選用，仍不可承諾鎖定狀態必然完成。
5. 保留主畫面上的手動「補同步」捷徑。初期檢查最近成功同步時間。

## 資料擷取

每次查詢最近 7 天至現在，而非只查最後一天；每週或手動重掃 30 天，補回延遲入庫資料。步數按本地日界線查詢每日累計，今天為部分日，日後覆寫；不能對混合來源樣本直接加總。以 iPhone 健康畫面逐日核對。若捷徑可用動作不能重現 Health 去重總數，停止該指標同步並回報限制，不假造精確值。

體重轉 kg；體脂來源若是 0–1 比例則乘 100，必須核對樣本單位，避免把 23% 再乘 100。心率先選定每日平均或靜息心率及來源，缺值略過。保留量測時間、來源、時區、穩定樣本 key。API 拒絕超範圍與未支援指標。

## 驗證協定候選

捷徑環境是否能可靠產生 HMAC 必須先驗證，不假設內建有此動作。可先採 HTTPS POST body 中的高熵、每裝置可輪替 bearer 憑證；它不出現在 URL、GitHub、PWA、同步日誌或回應。服務端先驗證憑證摘要與固定擁有者，再處理任何資料；使用 constant-time 摘要比較。此憑證可遭竊重放，故保留撤銷與 requestId 去重，不能稱為防重放簽章。

若需要更強的防重放，須先驗證支援簽章的原生捷徑能力或經使用者同意的本機 helper；協定使用 timestamp ±5 分鐘、nonce、canonical payload SHA-256、HMAC-SHA256，服務端持久保存 nonce 至期限後。未簽章成功不得啟用此模式。不要偷偷依賴付費第三方 App。

Apps Script doPost 的 event 不提供任意 request header 的一般讀取介面；因此不要假設可以讀取 Authorization header。原生捷徑 HTTP 請求不受瀏覽器 CORS 限制，但仍必須驗證 redirect、回應為 JSON 而非 Google 登入 HTML、以及伺服器認證確實執行。公開可達的 deployment 對每次讀寫都先認證；未帶憑證回應不得含任何健康資料。

## 重試與去重

成功以 `{ok:true, requestId, acceptedCount}` 判定，不單憑 HTTP 200；Apps Script 錯誤也可能在 JSON 中。每個批次固定 requestId，短暫失敗可重試 2 次，之後待下次 7 天回掃；不在背景長時間等待。固定唯一鍵讓重掃與部分失敗安全。

若要保存 outbox，僅保存待同步時間範圍與 requestId，避免把健康 payload 放在可能同步到 iCloud 的捷徑資料夾。若不提供本機持久 outbox，文件必須說明 7 天以外失敗需要手動選擇 30 天／自訂日期回掃，不能聲稱永不遺漏。

## 實機驗收

- iPhone 解鎖／鎖定、低耗電模式、飛航模式及重新連線。
- 拒絕任一健康權限、撤銷 API 憑證、Google 授權撤銷。
- 同批次重送 3 次：筆數不增加；同日步數更新後只覆寫。
- 模擬第 2 表寫入失敗，重送可修復且無重複。
- 不含憑證、錯誤憑證、過期簽章（若採用）不可讀寫。
- 午夜、旅行更換時區及夏令時間的總步數與健康 App 一致。
- 斷網超過 7 天後手動回掃並檢查 SyncLogs；日誌無敏感 payload。

這些測試需要使用者 iPhone 與 Apple Health 授權，目前尚未執行。
